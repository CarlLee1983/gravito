# Gravito 技術規格輸出範本

此範本定義 Gravito-Architect 技能生成技術文檔的標準結構。

## 輸出結構

### 1. 模組概覽 (Overview)

**格式**：
```markdown
## 模組概覽

**定義**：[用一句話定義該模組的核心功能]

**核心職責**：
- [職責 1]：[簡要說明]
- [職責 2]：[簡要說明]
- [職責 3]：[簡要說明]
```

**撰寫指引**：
- 定義必須精準且完整，讓讀者在 10 秒內理解模組用途
- 核心職責使用條列式，每項不超過一行
- 避免實作細節，專注於「做什麼」而非「如何做」

- 使用完整的 TypeScript 型別簽名
- 參數說明必須包含：資料型別、用途、合法範圍/約束

## 範例：完整輸出

```markdown
# Atlas QueryBuilder 技術規格

## 模組概覽

**定義**：QueryBuilder 是 Atlas ORM 的核心查詢構建器，負責將鏈式 API 轉換為 SQL 查詢語句。

**核心職責**：
- 提供鏈式 API（`select()`, `where()`, `join()`）構建查詢
- 將方法呼叫轉換為參數化 SQL 語句
- 支援關聯查詢的自動 JOIN 生成

## 技術規格

### 核心類別/介面

#### `QueryBuilder<T>`

**目的**：提供類型安全的查詢構建 API

**主要方法**：

##### `where(field: keyof T, operator: Operator, value: any): this`

- **參數**：
  - `field`：模型欄位名稱（型別安全）
  - `operator`：比較運算子（`'='`, `'>'`, `'LIKE'` 等）
  - `value`：比對值
- **回傳值**：返回 `this` 支援鏈式呼叫
- **行為**：將條件加入內部 `_conditions` 陣列
- **異常**：若 `field` 不存在於模型，拋出 `TypeError`

**範例**：
\`\`\`typescript
const users = await User.query()
  .where('age', '>', 18)
  .where('status', '=', 'active')
  .execute();
\`\`\`

### 資料流向

1. **輸入階段**：接收鏈式方法呼叫，驗證欄位存在性
2. **處理階段**：累積條件至內部狀態（`_conditions`, `_joins`）
3. **輸出階段**：`execute()` 時生成參數化 SQL 並執行

## 關鍵設計決策

### 決策 1：使用鏈式 API 而非物件配置

**問題背景**：初期考慮 `query({ where: [...] })` 的物件語法

**選擇方案**：採用鏈式 API（`query().where().join()`）

**理由**：
- 更符合 ActiveRecord 模式的直覺
- 支援條件動態組合（如：根據參數決定是否加 `where`）

**替代方案**：物件配置語法更易於序列化，但不適合複雜查詢的動態組合

**影響範圍**：需實作 `Proxy` 處理延遲執行

### 決策 2：異步執行而非同步返回

**問題背景**：是否應該在 `where()` 時立即查詢？

**選擇方案**：延遲執行，僅在 `execute()` / `first()` 時查詢

**理由**：
- 避免過早查詢導致的 N+1 問題
- 允許查詢優化器在執行前分析完整查詢樹

## 效能與擴展性

### 效能優化點

1. **查詢快取**
   - **優化前問題**：相同查詢重複執行
   - **優化手段**：基於 SQL + 參數的 LRU 快取
   - **效果**：重複查詢從 50ms 降至 <1ms

### 複雜度分析

- **時間複雜度**：單次查詢 O(n + m)，n 為條件數，m 為 JOIN 層數
- **空間複雜度**：O(n)，條件陣列的記憶體佔用

### 擴展性考量

- **水平擴展**：支援，查詢構建無狀態
- **垂直擴展**：受限於資料庫連線池大小
- **瓶頸點**：複雜 JOIN 時的 SQL 生成效能（當前未優化）

## 邊際案例與限制

### 已知限制

1. **不支援子查詢**
   - **現象**：無法在 `where()` 中使用子查詢
   - **影響**：複雜條件需拆分為多次查詢
   - **規避方式**：使用 `whereRaw()` 手動編寫 SQL

### 邊際案例處理

- **空輸入**：`where(null)` 拋出 `TypeError`
- **異常資料**：`where('invalid_field')` 在執行時拋出 `FieldNotFoundError`
- **併發衝突**：無鎖機制，依賴資料庫層級的交易隔離

### 潛在風險

- **N+1 查詢問題**：已避免，使用 `Eager Loading` 預載關聯
- **記憶體洩漏風險**：無，每次查詢創建新實例
- **Race Condition**：存在於並發更新場景，建議使用 `Model.lock()` 加鎖

## 後續優化建議

### 短期改進 (1-2 週)

1. **支援子查詢語法**
   - **目的**：降低複雜查詢的實作成本
   - **預期效果**：減少 30% 的 `whereRaw()` 使用

### 中期重構 (1-3 個月)

1. **引入查詢計畫分析器**
   - **目的**：在執行前偵測 N+1、笛卡爾積等問題
   - **風險評估**：需額外 10-20ms 分析時間

### 長期演進 (6 個月以上)

1. **支援分散式查詢**
   - **願景**：跨資料庫分片的查詢合併
```
