# Galaxy Blueprints Guide

`@gravito/scaffold` is more than a boilerplate generator; it's an architectural enforcer. This guide covers how to use Blueprints to build a consistent **Gravito Galaxy**.

## 1. Choosing an Architecture Type

Every Galaxy starts with a choice of complexity.

- **`enterprise-mvc`**: Best for standard business applications with high productivity needs.
- **`clean`**: Focused on the core domain, perfect for mission-critical logic that must be decoupled from infrastructure.
- **`ddd`**: Designed for complex ecosystems where multiple bounded contexts coexist.

```bash
# Initialize a new DDD Satellite
bun gravito make:satellite inventory --architecture ddd
```

## 2. The Stub Generator

Customize how code is generated by modifying or creating new **Stubs**.

```typescript
import { StubGenerator } from '@gravito/scaffold'

const generator = new StubGenerator()
const output = generator.render('export class {{pascalCase name}}Service {}', { name: 'catalog' })
// Result: export class CatalogService {}
```

## 3. Designing a Custom Blueprint

You can extend the framework by defining your own Blueprints for specific company standards.

```typescript
export class CorporateBlueprint extends BaseGenerator {
  getDirectoryStructure(context) {
    return [
      { type: 'directory', name: 'governance', children: [...] },
      { type: 'file', name: 'README.md', content: '# Corporate Standard' }
    ]
  }
}
```

## 4. Manifest Generation

Every Satellite must have a `manifest.json`. Scaffold ensures this is generated with the correct metadata for the `@gravito/xenon` host.

```json
{
  "name": "@satellites/orders",
  "version": "1.0.0",
  "architecture": "ddd",
  "dependencies": ["@gravito/atlas", "@gravito/signal"]
}
```

## 5. Automated Testing Setup

A blueprint is not complete without tests. Scaffold automatically generates Vitest/Bun-test suites for every new component.

```bash
# Generate a service with its test
bun gravito make:service AuthService --test
```
