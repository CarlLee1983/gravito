# Builder 物件池決策文檔

## 決策摘要

**決定：** 暫不實作 Builder 物件池，作為 v1.1.0 的可選功能保留到未來版本。

**決策日期：** 2026-01-31

## 背景

在規劃 Dark Matter v1.1.0 時，Builder 物件池被列為第四個優化項目，目的是減少高頻場景（10k+ RPS）下的 GC 壓力和記憶體碎片化。

## 分析過程

### 1. 問題評估

**問題：** 每次查詢建立新的 MongoQueryBuilder 實例

**影響範圍：**
- 高頻場景（>10k RPS）
- 記憶體受限環境
- 對延遲敏感的應用

**影響程度：** 中等（僅在極高負載下顯著）

### 2. 複雜度評估

**實作複雜度：** 中等
- 需要實作物件池管理
- 需要處理物件重置邏輯
- 需要處理併發安全性
- 需要提供監控 API

**維護複雜度：** 中等
- 增加程式碼維護成本
- 需要額外的測試覆蓋
- 增加使用者學習成本

**風險：**
- 物件池實作錯誤可能導致記憶體洩漏
- 狀態重置不完整可能導致資料污染
- 增加除錯難度

### 3. 效益評估

**預期效益：**
- 記憶體使用減少：30-50%
- GC 次數減少：40-60%
- 吞吐量提升：15-25%
- P99 延遲改善：10-20%

**實際效益取決於：**
- 實際 RPS（是否真的達到 10k+）
- JavaScript 引擎（V8/JavaScriptCore 的 GC 效能）
- 記憶體環境（是否真的受限）
- 查詢複雜度（簡單查詢受益較小）

### 4. 替代方案

**現代 JavaScript 引擎的優化：**
1. 分代 GC 對短生命週期物件處理效率高
2. 內聯快取（Inline Caching）優化物件建立
3. 逃逸分析（Escape Analysis）可能棧上分配

**其他優化手段：**
1. 索引優化（效益更高）
2. 連接池配置
3. 批次操作
4. 查詢優化

## 決策理由

### 暫不實作的原因

1. **適用場景有限**
   - 大多數應用 RPS < 5k
   - 只有極高負載才需要
   - 過早優化風險

2. **複雜度 vs 效益**
   - 實作和維護成本高
   - 實際效益需驗證
   - 其他優化手段可能更有效

3. **使用者體驗**
   - 增加 API 複雜度
   - 需要理解何時啟用
   - 可能引入新問題

4. **核心功能優先**
   - v1.1.0 已有三個核心功能
   - 功能完整性更重要
   - 可在後續版本評估

### 保留未來實作的理由

1. **確實有潛在價值**
   - 在極高負載下可能有顯著效益
   - 部分使用者可能需要

2. **架構已考慮**
   - 實作方案已設計
   - 測試策略已規劃
   - API 設計已確定

3. **可選功能**
   - 可作為進階功能提供
   - 不影響現有 API
   - 向後相容

## 未來評估標準

### 何時重新考慮實作

滿足以下**任一**條件：

1. **使用者回饋**
   - 收到多個高負載場景的效能問題回報
   - 使用者主動要求物件池功能

2. **效能數據**
   - 實際場景測試顯示 Builder 建立開銷 > 20%
   - 記憶體分析顯示大量 Builder 物件堆積
   - GC 暫停時間影響業務

3. **基準測試**
   - 建立完整的基準測試套件
   - 測試顯示物件池效益 > 30%
   - 無顯著副作用

### 評估流程

1. **收集資料**
   - 使用者回饋
   - 實際使用場景效能數據
   - 基準測試結果

2. **量化分析**
   - 建立基準測試
   - 測量實際效益
   - 評估複雜度成本

3. **決策**
   - 效益 > 成本 → 實作
   - 效益 < 成本 → 提供其他優化建議
   - 不確定 → 收集更多資料

## 替代建議

### 給高負載場景使用者的建議

如果遇到效能問題，按優先順序嘗試：

1. **索引優化**（最高優先）
   ```typescript
   await Mongo.collection('users').createIndex({ status: 1 })
   ```

2. **查詢優化**
   ```typescript
   // 使用投影減少資料傳輸
   .select('name', 'email')
   ```

3. **連接池調整**
   ```typescript
   maxPoolSize: 50,  // 根據負載調整
   minPoolSize: 10
   ```

4. **批次操作**
   ```typescript
   await Mongo.collection('users').bulkWrite([...])
   ```

5. **快取層**
   ```typescript
   // 使用 Redis 等快取常用查詢
   ```

6. **讀寫分離**
   ```typescript
   // 使用 MongoDB replica set 的讀寫分離
   ```

### 自定義物件池

如果確實需要，使用者可以實作自己的物件池：

```typescript
class CustomBuilderPool {
  private pool: MongoQueryBuilder[] = []

  acquire() {
    return this.pool.pop() || Mongo.collection('users')
  }

  release(builder: MongoQueryBuilder) {
    // 重置 builder 狀態
    this.pool.push(builder)
  }
}
```

## 結論

Builder 物件池是一個有價值的優化方向，但考慮到：
- 適用場景有限
- 實作複雜度
- 現有替代方案
- 核心功能優先

決定在 v1.1.0 中**暫不實作**，保留為未來可選功能。

此決策可以在收集到足夠的使用者回饋和效能數據後重新評估。
