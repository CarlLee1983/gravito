## 1. 模組概述

### 1.1 功能定位

**@gravito/flare** 是 Gravito 框架的多通道通知系統，提供：

- 多通道通知投遞（Mail、Database、Broadcast、Slack、SMS）
- 佇列支援（與 `@gravito/stream` 整合）
- Fluent API（直觀的通知定義方式）
- 可擴展的通道架構
- 類型安全的通知載荷

### 1.2 架構結構

```
flare/src/
├── index.ts                    # 模組入口
├── OrbitFlare.ts               # Gravito Orbit 實現
├── Notification.ts             # 通知基類
├── NotificationManager.ts      # 核心通知管理器
├── types.ts                    # 類型定義
└── channels/
    ├── MailChannel.ts          # 郵件通道
    ├── DatabaseChannel.ts      # 資料庫通道
    ├── BroadcastChannel.ts     # 即時廣播通道
    ├── SlackChannel.ts         # Slack 通道
    └── SmsChannel.ts           # SMS 通道
```

### 1.3 依賴關係

| 模組 | 類型 | 必需性 |
|------|------|--------|
| @gravito/core | Dependency | 必需 |
| @gravito/stream | Peer | 可選（佇列支援）|
| @gravito/signal | Peer | 可選（郵件服務）|
| @gravito/radiance | Peer | 可選（廣播服務）|

## 2. 現況分析

### 2.1 代碼品質評分

| 維度 | 評分 | 備註 |
|------|------|------|
| 架構設計 | 8.0/10 | 通道抽象清晰，缺少批次處理 |
| 代碼品質 | 7.5/10 | 類型斷言較多，錯誤處理可改進 |
| 測試覆蓋 | 7.0/10 | 基本覆蓋，缺少錯誤路徑測試 |
| 文檔完整性 | 8.0/10 | README 清晰，JSDoc 可補充 |
| 效能最佳化 | 7.0/10 | 序列發送，缺少並行/批次機制 |
| 類型安全 | 8.5/10 | 類型完整，部分使用 `as` 斷言 |

### 2.2 優勢

- ✅ 通道抽象設計良好，易於擴展
- ✅ 支援佇列延遲發送
- ✅ 錯誤不中斷其他通道
- ✅ 完善的 Gravito 整合
- ✅ 類型定義完整

### 2.3 待改善

- ⚠️ 通道錯誤只記錄不拋出，難以追蹤
- ⚠️ 缺少通知發送事件/Hook
- ⚠️ 缺少批次發送支援
- ⚠️ SMS 通道 AWS SNS 未實現
- ⚠️ 缺少重試機制
- ⚠️ 序列化僅處理淺層物件
- ⚠️ OrbitFlare 中大量類型斷言

## 3. 問題清單與優先級

### P1 - 緊急（必須立即修復）

| 編號 | 問題 | 風險等級 | 影響範圍 |
|------|------|----------|----------|
| P1-01 | 通道錯誤無法被調用方捕獲 | 高 | 所有通知發送 |
| P1-02 | `toMail()` 等方法預設拋出錯誤但類型標記為可選 | 中 | 類型安全 |
| P1-03 | 序列化方法不處理巢狀物件和日期 | 中 | 佇列通知 |

### P2 - 重要（下一版本修復）

| 編號 | 問題 | 風險等級 | 影響範圍 |
|------|------|----------|----------|
| P2-01 | 缺少通知生命週期 Hook | 中 | 監控/追蹤 |
| P2-02 | 多通道序列發送效能差 | 中 | 大量通知 |
| P2-03 | 缺少批次發送 API | 中 | 大量接收者 |
| P2-04 | OrbitFlare 類型斷言過多 | 低 | 代碼品質 |
| P2-05 | 缺少通道配置驗證 | 中 | 配置錯誤 |

### P3 - 優化（可排入未來版本）

| 編號 | 問題 | 風險等級 | 影響範圍 |
|------|------|----------|----------|
| P3-01 | 缺少重試機制 | 低 | 故障恢復 |
| P3-02 | 缺少發送指標監控 | 低 | 營運可觀察性 |
| P3-03 | AWS SNS SMS 未實現 | 低 | SMS 功能完整性 |
| P3-04 | 缺少通知模板系統 | 低 | 開發者體驗 |

## 6. 風險評估

### 6.1 技術風險

| 風險 | 可能性 | 影響 | 緩解措施 |
|------|--------|------|----------|
| 並行發送導致 rate limit | 中 | 中 | 添加可配置的並發限制 |
| Hook 過多影響效能 | 低 | 低 | 使用非同步 Hook，不阻塞主流程 |
| 批次發送部分失敗 | 中 | 中 | 返回詳細結果，支援部分重試 |
| 序列化改動破壞相容性 | 低 | 高 | 保持向後相容，新增而非修改 |

### 6.2 相容性風險

| 風險 | 可能性 | 影響 | 緩解措施 |
|------|--------|------|----------|
| 錯誤處理改動破壞現有邏輯 | 中 | 中 | 提供 `throwOnError` 選項 |
| 新 Hook 與現有整合衝突 | 低 | 低 | Hook 為可選功能 |

### 6.3 向後相容性承諾

- P1 修復：維持完全向後相容，新增功能為可選
- P2 功能：所有新功能為可選，預設行為不變
- P3 優化：所有新功能為可選
