## 📋 概述

本文檔詳細描述 Flash Sale 系統的分片架構設計，目標是通過數據庫分片實現 **10 倍 QPS 提升**（1K → 10K+），同時保持數據一致性和系統可維護性。

### 核心目標

| 指標 | 當前 | 目標 | 提升 |
|------|------|------|------|
| 最大 QPS | 1,000 | 10,000+ | 10x ⬆️ |
| 單分片負載 | 1,000 req/s | 125 req/s | 8x ⬇️ |
| 查詢延遲 | 12ms | < 8ms | 33% ⬇️ |
| 可擴展性 | 單機限制 | 線性擴展 | 無限 |

## 🏗️ 架構設計

### 1. 分片策略

#### 選擇依據

| 方案 | 優點 | 缺點 | 選擇 |
|------|------|------|------|
| **Range 分片** | 簡單實現 | 熱點問題、不均衡 | ❌ |
| **Hash 分片** | 分佈均勻、簡單 | 擴展複雜 | ✅ 選中 |
| **一致性哈希** | 最小化遷移 | 複雜度高 | ✅ 優先使用 |
| **目錄分片** | 靈活精準 | 高維護成本 | 備選 |

**決策**：採用 **一致性哈希** + **虛擬節點** 機制

#### 分片鍵

```
分片鍵：userId
原因：
- 用戶訂單的主要查詢維度
- userId 分佈均勻（避免熱點）
- 方便跨分片聚合（按用戶分類）
- 便於後續用戶層面的轉移
```

#### 分片數量

```typescript
分片數量：8 個分片

計算依據：
- 當前 QPS 1,000 req/s
- 目標 QPS 10,000 req/s
- 10,000 ÷ 1,000 = 10 倍
- 實際分片數：8（保守估計，便於未來擴展至 16/32）

優勢：
- 2^3 = 8（2 的冪次，二分查找優化）
- 每個分片承載 125 req/s（安全邊際）
- 便於後續動態擴展（增至 16 時無需全量遷移）
```

### 2. 一致性哈希實現

#### 算法原理

```
哈希環結構：
- 哈希值範圍：0 ~ 2^32 - 1（4 GB）
- 物理節點 8 個
- 虛擬節點 160 個（每個物理節點 20 個）
- 總虛擬節點 1,280 個

優勢：
- 節點均衡分佈
- 新增節點時只需遷移 1/n 的數據
- 節點故障時只影響相鄰節點

示例：
  添加 shard-0：
  ├─ 虛擬節點 shard-0:0  -> hash: 0x12345678
  ├─ 虛擬節點 shard-0:1  -> hash: 0x87654321
  ├─ 虛擬節點 shard-0:2  -> hash: 0xabcdef00
  └─ ...共 160 個虛擬節點
```

#### 實現細節

**文件**：`src/sharding/ConsistentHash.ts`

```typescript
class ConsistentHash {
  private ring: Map<number, string>      // hash -> 物理節點名
  private sortedKeys: number[]           // 排序的 hash 值
  private nodes: Set<string>             // 物理節點集合
  private virtualNodes: number           // 每個節點的虛擬節點數

  // 核心方法：
  - addNode(node: string)                // O(v log v) 添加節點
  - removeNode(node: string)             // O(v log v) 移除節點
  - getNode(key: string)                 // O(log n) 查詢最近節點
  - getNodes(key, count)                 // O(n) 查詢前 N 個節點
}
```

**性能指標**：

| 操作 | 時間複雜度 | 說明 |
|------|-----------|------|
| 查詢單個節點 | O(log n) | 二分查找 |
| 添加節點 | O(v log v) | v = 虛擬節點數 = 160 |
| 移除節點 | O(v log v) | 移除 160 個虛擬節點 |
| 獲取前 N 個 | O(n) | 用於複製 |

### 3. 分片路由表

#### 路由表設計

```typescript
interface RoutingTable {
  shardId: number          // 分片 ID (0-7)
  nodeId: string           // 物理節點 ID (shard-0 to shard-7)
  isPrimary: boolean       // 是否為主分片
  replicas: string[]       // 副本位置（用於後續複製）
}

// 示例
userId "user:123456"
  -> hash: 0x3f4a2b1c
  -> 環上最近節點：shard-3:85
  -> 分片 ID：3
  -> 路由：{shardId: 3, nodeId: 'shard-3', isPrimary: true}
```

性能收益：

## 📊 性能分析

### 查詢路徑分解

#### 單分片查詢（快路徑）

```
用戶查詢 (userId)
  ↓ (1ms)
計算分片 ID (一致性哈希)
  ↓ (0.5ms)
連接池獲取連接
  ↓ (0.2ms)
執行 SQL 查詢
  ↓ (8ms - 12ms)
返回結果

總時間：9.7ms - 13.7ms（目標 < 8ms 需優化）
```

#### 跨分片聚合查詢（複雜路徑）

```
聚合查詢 (如總銷售額)
  ↓
並行查詢 8 個分片
  ├─ Shard-0: 8ms
  ├─ Shard-1: 9ms
  ├─ Shard-2: 8.5ms
  ├─ ...
  └─ Shard-7: 9.5ms
  ↓ (max 12ms - 聚合響應時間)
合併結果 (1ms)
  ↓
返回聚合結果

總時間：< 50ms（允許範圍）
```

### 負載均衡驗證

```
理想分佈：
Shard-0: 125 req/s ✓
Shard-1: 125 req/s ✓
...
Shard-7: 125 req/s ✓

總計：1,000 req/s

數據驗證方法：
1. 監控每個分片的 requestCount
2. 計算標準差（理想 = 0）
3. 定期報告分佈不均匀度
4. 觸發重平衡機制
```

## 📈 擴展性設計

### 從 8 分片擴展至 16 分片

```
當前：8 分片 × 125 req/s = 1,000 req/s
目標：16 分片 × 125 req/s = 2,000 req/s

遷移策略（一致性哈希優勢）：
1. 添加新的 8 個分片（shard-8 到 shard-15）
2. 重新構建哈希環
3. 受影響的數據：≈ 50%（每個舊分片遷移 25% 的數據）
4. 影響時間：最小化（增量遷移）
5. 零停機：使用雙寫或影子流量

vs Hash 分片（需全量遷移）：
- 受影響數據：100%
- 停機時間：不可接受
```

### 故障恢復設計

```
場景：shard-3 故障

對用戶的影響：
- 用戶 A（routed to shard-3）：請求失敗
- 用戶 B（routed to shard-1）：無影響

恢復流程：
1. 監控檢測故障（連接失敗）
2. 標記 shard-3 為 unhealthy
3. 觸發 failover（轉移至副本或讀取副本）
4. 通知運維進行修復
5. 修復完成後重新標記為 healthy
```
