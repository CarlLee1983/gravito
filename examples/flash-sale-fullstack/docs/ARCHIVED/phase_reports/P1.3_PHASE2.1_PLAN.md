# P1.3 Phase 2.1 - 快速路徑優化計劃

## 問題根源分析

### 當前瓶頸

在基準測試中發現：
- **提交吞吐量**：133 ops/sec（目標 5000+ ops/sec）
- **最大隊列深度**：539（當提交 1000 個事件時）
- **平均延遲**：~100ms per submission

### 根本原因：背壓過度激活

**BackpressureManager 當前配置**：
```
moderateThreshold: 100    // 隊列 > 100 時激活中度背壓
highThreshold: 500        // 隊列 > 500 時激活高背壓
criticalThreshold: 1000   // 隊列 > 1000 時激活關鍵背壓
```

**問題**：
1. 隊列深度只達到 100 時就開始延遲 LOW 優先級事件（50ms）
2. 隊列深度達到 500 時開始延遲 NORMAL 優先級事件（50ms）
3. 延遲累積導致提交速度大幅下降
4. 測試中大部分提交延遲發生在背壓延迟中

**實測延遲分布**：
```
隊列深度 100:   LOW 事件延迟 50ms → 總延遲 50ms
隊列深度 500:   NORMAL 事件延迟 50ms → 總延遲 50ms
隊列深度 539:   最大隊列深度（測試中止）
```

## Phase 2.1 優化策略

### 策略 1：提高背壓激活閾值

**變更**：
```typescript
// 舊配置
moderateThreshold: 100
highThreshold: 500
criticalThreshold: 1000

// 新配置
moderateThreshold: 1000   // 提高 10 倍
highThreshold: 2000       // 提高 4 倍
criticalThreshold: 4000   // 提高 4 倍
maxQueueDepth: 10000      // 提高 2 倍
```

**理由**：
- 允許隊列積累更多事件而不激活背壓
- 使系統能承受更高峰值負載
- L1 隊列可以充當緩衝，吸收突發流量

**預期效果**：
- 延遲激活點從 100 → 1000
- 減少不必要的延遲
- 提升吞吐量到 1000+ ops/sec

### 策略 2：減少延遲時間

**變更**：
```typescript
// 舊延遲
MODERATE: 50ms per event
HIGH: 50-100ms per event
CRITICAL: 200ms per event

// 新延遲（降低 50-80%）
MODERATE: 10ms per event
HIGH: 20ms per event
CRITICAL: 50ms per event
```

**理由**：
- 背壓延遲不應超過基本操作延遲 (~1ms)
- 當前 50-200ms 延遲是提交開銷的 50-200 倍
- 減少延遲有助於保持吞吐量

**預期效果**：
- 降低平均延遲 50-80%
- 即使在高背壓下仍保持合理吞吐量

### 策略 3：實施漸進式背壓而非急劇變化

**變更**：
```typescript
// 舊策略：固定延遲
if (queueDepth > 100) {
  await delay(50)  // 固定延遲
}

// 新策略：根據隊列深度的延遲
const delay = calculateAdaptiveDelay(queueDepth)

calculateAdaptiveDelay(queueDepth) {
  // 線性計算：隊列越深，延遲越多
  const ratio = (queueDepth - threshold) / maxQueueDepth
  return baseDelay * ratio  // 漸進式增加
}
```

**理由**：
- 避免在閾值處出現延遲跳躍
- 提供更平滑的背壓曲線
- 更好地利用隊列容量

**預期效果**：
- 更均勻的延遲分布
- 較少的延遲尖峰
- 更可預測的吞吐量

### 策略 4：優先級更新

**變更**：
```typescript
// 舊策略：按優先級分層延遲
CRITICAL: 無延遲
HIGH: 無延遲
NORMAL: 50ms @ HIGH
LOW: 50ms @ MODERATE, 拒絕 @ CRITICAL

// 新策略：所有優先級都延遲，但速率不同
const delayByPriority = {
  CRITICAL: 0,        // 無延遲
  HIGH: adapterDelay * 0.5,   // 50% 延遲
  NORMAL: adaptiveDelay * 1.0,  // 100% 延遲
  LOW: adaptiveDelay * 2.0      // 200% 延遲（或拒絕）
}
```

**理由**：
- 公平對待所有優先級
- CRITICAL 始終優先通過
- 低優先級在高負載下更敏感

## 代碼更改概覽

### 文件：BackpressureManager.ts

**更改 1**：配置更新
```typescript
// 舊
moderateThreshold: 100
highThreshold: 500
criticalThreshold: 1000

// 新
moderateThreshold: 1000
highThreshold: 2000
criticalThreshold: 4000
```

**更改 2**：延遲計算優化
```typescript
// 新增方法
calculateAdaptiveDelay(
  eventPriority: EventPriority,
  queueDepth: number
): number {
  const state = this.getBackpressureState(queueDepth)
  const baseDelay = PRIORITY_DELAY_FACTORS[eventPriority]

  // 漸進式計算
  const ratio = Math.max(0,
    (queueDepth - this.getThresholdForState(state)) /
    (this.config.maxQueueDepth - this.getThresholdForState(state))
  )

  return baseDelay * ratio
}
```

**更改 3**：應用新延遲計算
```typescript
async applyBackpressure(
  eventPriority: EventPriority,
  queueDepth: number
): Promise<boolean> {
  // ... 現有邏輯 ...

  // 使用新的適應性延遲
  const delay = this.calculateAdaptiveDelay(
    eventPriority,
    queueDepth
  )

  if (delay > 0) {
    await this.applyDelay(delay)
  }

  return true
}
```
