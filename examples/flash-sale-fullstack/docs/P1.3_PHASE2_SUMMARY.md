## 🔍 問題分析

### 主要瓶頸：EventAggregator.submit() 性能

**症狀**：
- 2000 次提交耗時 ~15 秒
- 吞吐量 133 ops/sec（目標 5000+ ops/sec）
- 隊列背壓激活，深度 539

**可能原因**：
1. 背壓管理器邏輯過於嚴格
2. 去重算法性能不佳
3. 隊列操作複雜度未優化
4. 事件對象深複製開銷

**改進策略**：
- Phase 2.1：背壓算法調整（30 min）
- Phase 2.2：隊列和去重優化（60 min）
- Phase 2.3：性能驗證（60 min）

## 📋 Phase 2.1-2.3 優化計劃

### Phase 2.1 - 快速路徑優化 (1 h)

1. **背壓算法調整** (20 min)
   - 增加初始背壓閾值（從 50% → 80%）
   - 漸進式背壓升級而非急劇變化
   - 優化狀態轉換邏輯

2. **隊列操作優化** (30 min)
   - 分析二叉堆 bubble up/down 複雜度
   - 考慮使用循環緩衝區
   - 減少內存分配

3. **去重優化** (10 min)
   - 實施布隆過濾器快速路徑
   - 優化模式匹配算法

### Phase 2.2 - 內存與批處理優化 (1 h)

1. **對象池模式** (20 min)
   - 實現 CacheEvent 對象池
   - 減少 GC 壓力

2. **批量提交支持** (30 min)
   - 優化 submitBatch() 實現
   - 減少同步開銷

3. **內存局部性改進** (10 min)
   - 減少隨機訪問
   - 改善 CPU 快取利用

### Phase 2.3 - 驗證與調優 (1 h)

1. **基準重測** (20 min)
   - 運行完整基準測試
   - 驗證優化效果

2. **負載測試** (30 min)
   - 恆定負載測試
   - 漸進式負載測試
   - 波動負載測試

3. **參數調優驗證** (10 min)
   - 驗證各場景參數
   - 文檔化最佳實踐
