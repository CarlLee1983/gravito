## ADR-001: Satellite 微服務架構

### 背景

搶購系統需要支持高併發業務邏輯，涉及商品管理、庫存控制、訂單處理和支付等多個業務域。

### 決策

使用 **Gravito 的 Satellite 架構**將系統分解為獨立的業務單元：

```
Core (PlanetCore)
├── Orbits (基礎設施)
│   ├── Database (Atlas)
│   ├── Events (Signal)
│   └── Queues (Stream)
└── Satellites (業務領域)
    ├── Flash-Sale (搶購)
    ├── Inventory-Lock (庫存)
    └── Payment (支付)
```

### 核心 Satellites

#### 1. Flash-Sale Satellite
- **責任**：訂單建立、商品管理、訂單確認
- **事件**：`order:created`, `order:confirmed`, `order:failed`
- **依賴**：inventory-lock (鎖定庫存)

#### 2. Inventory-Lock Satellite
- **責任**：庫存預扣、死鎖偵測、庫存回滾
- **機制**：分佈式鎖 + 超時自動釋放
- **依賴**：redis (鎖存儲)

#### 3. Payment Satellite
- **責任**：支付流程、支付確認、失敗回滾
- **流程**：支付 → 庫存扣減 → 訂單確認
- **依賴**：stripe (支付網關)

### 優點

✅ **高內聚**：每個 satellite 負責一個業務域
✅ **低耦合**：通過事件系統通訊，不直接依賴
✅ **獨立部署**：各 satellite 可獨立版本管理
✅ **易於測試**：業務邏輯與基礎設施分離
✅ **擴展性**：新業務域可輕鬆新增 satellite

### 缺點

❌ **分佈式複雜性**：需要處理最終一致性
❌ **事件順序保證**：需要 saga 模式確保流程一致
❌ **除錯難度**：跨 satellite 追蹤需要分佈式追蹤

### 替代方案

| 方案 | 優點 | 缺點 |
|------|------|------|
| **單體應用** | 開發簡單 | 難以擴展，耦合高 |
| **無狀態微服務** | 完全獨立 | 通訊開銷大，複雜度高 |
| **Satellite 架構** | 平衡點 | 學習曲線 |

### 決策結果

✅ **採用 Satellite 架構**（現有）

## ADR-002: 非同步隊列策略

### 背景

搶購系統的核心流程涉及多個步驟：
1. 訂單建立 → 2. 庫存鎖定 → 3. 支付處理 → 4. 庫存扣減 → 5. 訂單確認

同步執行會導致超時，需要非同步處理。

### 決策

使用 **Bull 消息隊列**實現非同步訂單流程：

```
OrderCreated Event
    ↓
[Lock Inventory Job] → 成功 → [Deduct Inventory Job]
    ↓                              ↓
    失敗                      [Confirm Order Job]
    ↓                         ↓
[Release Inventory Job]    訂單確認完成
```

### Job 定義

#### 1. LockInventoryJob
```
輸入：orderId, productId, quantity
輸出：lockId (庫存鎖定 ID)
重試：3 次，5 秒後退
```

#### 2. DeductInventoryJob
```
輸入：orderId, lockId
流程：
  1. 扣減庫存
  2. 成功 → ConfirmOrderJob
  3. 失敗 → ReleaseInventoryJob
```

#### 3. ConfirmOrderJob
```
輸入：orderId, lockId
流程：
  1. 確認訂單
  2. 觸發 order:confirmed 事件
  3. 失敗 → 需人工介入
```

#### 4. ReleaseInventoryJob
```
輸入：orderId, lockId
流程：
  1. 釋放庫存鎖定
  2. 恢復庫存
  3. 觸發 order:cancelled 事件
```

### 優點

✅ **高吞吐**：支持高併發訂單
✅ **容錯**：自動重試，失敗隔離
✅ **可監控**：每個 job 狀態可追蹤
✅ **解耦**：異步處理減少耦合

### 缺點

❌ **最終一致性**：需要處理中間狀態
❌ **死信隊列**：Job 永久失敗需人工介入
❌ **監控複雜**：需要額外的監控系統

### 替代方案

| 方案 | 優點 | 缺點 |
|------|------|------|
| **同步 RPC** | 簡單、強一致性 | 超時、性能差 |
| **事件溯源** | 完整歷史、可重放 | 複雜度高，儲存大 |
| **Bull 隊列** | 平衡、易實現 | 最終一致性 |

### 決策結果

✅ **採用 Bull 隊列**（現有）

## ADR-003: 分佈式鎖機制

### 背景

搶購系統的核心挑戰：在高併發下防止庫存超銷。

需要：
- 原子性操作
- 超時自動釋放
- 死鎖偵測

### 決策

使用 **Redis 分佈式鎖** + **超時機制**：

```lua
-- Lua 腳本：原子性鎖定與設置 TTL
if redis.call('exists', key) == 0 then
  redis.call('set', key, value, 'EX', ttl)
  return 1  -- 成功
else
  return 0  -- 已鎖定
end
```

### 鎖策略

#### 1. 鎖鍵設計
```
inventory:lock:{productId}:{quantity}:{userId}
```

#### 2. 超時策略
```
TTL = 15 分鐘
- 為用戶預留充足支付時間
- 超時自動釋放，防止鎖洩漏
```

#### 3. 重試機制
```
最多 3 次重試，每次間隔 5 秒
如果 3 次都失敗，觸發補償流程
```

### 死鎖偵測

```
監視長期未釋放的鎖：
1. 定期掃描超期鎖
2. 強制釋放 + 補償流程
3. 告警通知運維
```

### 優點

✅ **高效能**：O(1) 操作
✅ **自動釋放**：TTL 防止洩漏
✅ **簡單易用**：無需複雜協議
✅ **Redis 原生**：易於監控

### 缺點

❌ **Redis 單點**：需要 Cluster
❌ **無法保證**：Redis 重啟會失鎖
❌ **複雜邊界**：TTL 設置困難

### 替代方案

| 方案 | 優點 | 缺點 |
|------|------|------|
| **Zookeeper** | 強一致 | 複雜、性能低 |
| **etcd** | 成熟 | 額外依賴 |
| **Redis 鎖** | 簡單、高效 | 可靠性差 |
| **Redlock** | 容錯 | 無法真正分散 |

### 決策結果

✅ **採用 Redis 簡單鎖**（現有）
⚠️ **後續考慮 Redlock**（可靠性）

## ADR-004: 快取策略

### 背景

搶購系統的查詢操作（70% 是訂單建立，10% 是商品列表查詢）。

商品列表變化不頻繁（上架/下架），但被頻繁查詢。

### 決策

使用 **三層快取** 策略：

```
┌─────────────────────────────────┐
│   本地內存快取 (Warm-up)        │ TTL: 30秒
├─────────────────────────────────┤
│   Redis 快取層                   │ TTL: 5分鐘
├─────────────────────────────────┤
│   PostgreSQL 數據庫              │ 源數據
└─────────────────────────────────┘
```

### 快取配置

| 數據 | TTL | 層級 | 更新策略 |
|------|-----|------|--------|
| 商品列表 | 5分鐘 | Redis | 定時更新 |
| 商品詳情 | 5分鐘 | Redis | 定時更新 |
| 庫存狀態 | 60秒 | Redis | 立即更新 |
| 訂單狀態 | 60秒 | Redis | 事件更新 |

### 快取失效策略

#### 1. TTL 失效
```
自動過期，定期清理
```

#### 2. 事件驅動失效
```
訂單確認 → 清除商品詳情快取
庫存變更 → 清除庫存快取
```

#### 3. 模式匹配清理
```
deletePattern('product:*')  // 清除所有商品快取
deletePattern('order:*')    // 清除所有訂單快取
```

### 優點

✅ **高效率**：多數查詢命中快取
✅ **主動控制**：支持手動失效
✅ **可觀測**：快取命中率可追蹤
✅ **簡單實現**：無需複雜機制

### 缺點

❌ **數據一致性**：可能返回過期數據
❌ **記憶體成本**：需要充足的 Redis 記憶體
❌ **複雜性**：需要管理失效邏輯

### 替代方案

| 方案 | 優點 | 缺點 |
|------|------|------|
| **無快取** | 數據新鮮 | 性能差 |
| **被動快取** | 簡單 | 常命中失敗 |
| **主動快取** | 高效 | 管理複雜 |

### 決策結果

✅ **採用主動快取 + TTL 失效**（現有）

## ADR-005: 監控與可觀測性

### 背景

搶購系統需要實時瞭解系統狀態：
- 訂單成功率
- 性能指標
- 錯誤追蹤

### 決策

使用 **結構化日誌 + 性能指標** 策略：

```typescript
// 結構化日誌
logger.info('Order created', {
  orderId: '123',
  userId: '456',
  productId: '789',
  timestamp: new Date().toISOString(),
  duration: 234, // ms
})

// 性能指標
metrics.histogram('order.creation.time', duration)
metrics.counter('order.success', 1)
metrics.gauge('queue.size', queueSize)
```

### 關鍵指標

| 指標 | 目標 | 告警閾值 |
|------|------|--------|
| 訂單成功率 | 99.9% | < 99% |
| P99 延遲 | 500ms | > 1000ms |
| 隊列堆積 | < 100 | > 500 |
| 錯誤率 | < 0.1% | > 1% |

### 優點

✅ **實時可見**：快速發現問題
✅ **可追蹤**：完整的請求鏈路
✅ **自動告警**：及時通知

### 缺點

❌ **成本高**：日誌與指標存儲
❌ **複雜性**：需要監控系統
❌ **性能開銷**：日誌記錄影響性能

### 決策結果

✅ **使用結構化日誌** (現有)
🔄 **後續加入分佈式追蹤** (OpenTelemetry)

## ADR-006: 測試策略

### 背景

搶購系統涉及複雜的業務邏輯和多個 satellites。

需要確保：
- 單個 satellite 的正確性
- satellites 間的整合
- 高併發下的穩定性

### 決策

使用 **三層測試** 策略：

```
單元測試 (75%)
  ├─ Use Cases 測試
  ├─ Repository 測試
  └─ Service 測試

整合測試 (15%)
  ├─ API 端點測試
  ├─ 數據庫交互
  └─ Satellites 通訊

性能測試 (10%)
  ├─ k6 負載測試
  ├─ 瓶頸分析
  └─ 優化驗證
```

### 測試框架

- **單元/整合**：Bun test
- **E2E**：Playwright (計畫中)
- **性能**：k6

### 覆蓋率目標

- 最低：75%
- 目標：85%
- 核心模塊：95%

### 優點

✅ **高可信度**：充分的測試保障
✅ **快速反饋**：CI/CD 自動測試
✅ **文檔化**：測試即文檔

### 缺點

❌ **維護成本**：大量測試代碼
❌ **執行時間**：完整測試需時

### 決策結果

✅ **採用三層測試策略**（進行中）
