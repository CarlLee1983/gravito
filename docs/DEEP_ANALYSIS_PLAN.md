# Gravito Engine - 深度性能分析計劃

## 當前狀態

### Benchmark 結果
- **Gravito**: 81,664 req/s
- **Hono**: 83,413 req/s
- **差距**: -2.1% (落後 1,749 req/s)
- **目標**: +20% vs Hono = 100,096 req/s
- **需要提升**: +22.6% (18,432 req/s)

### 已完成的優化
1. ✅ URL 對象重用
2. ✅ Headers 對象重用
3. ✅ 零中間件快速路徑
4. ✅ collectMiddleware 早期返回

### 效果
- 第一輪優化帶來 +11.7% 提升
- 證明了「減少對象創建」的方向正確

## 分析方法

### 方法 1: 代碼對比分析 🔍

**目標**: 逐行對比 Gravito vs Hono 的熱路徑代碼

**步驟**:
1. 提取 Hono 的核心路由匹配代碼
2. 提取 Hono 的 Context 實作
3. 對比差異點：
   - 路由匹配算法
   - Context 創建方式
   - Response 構建方式
   - 中間件執行方式

**輸出**: 
- 差異清單
- 可借鑒的優化技巧

---

### 方法 2: 火焰圖分析 🔥

**目標**: 使用 Bun profiler 識別熱點函數

**步驟**:
1. 運行 Gravito 並生成 CPU profile
   ```bash
   bun --cpu-prof run examples/benchmarks/profile-gravito.ts
   oha -z 10s -c 100 http://localhost:3000/
   ```

2. 分析火焰圖，找出：
   - 哪些函數佔用最多 CPU 時間
   - 是否有意外的熱點
   - 函數調用層級是否過深

**輸出**:
- 熱點函數清單（按 CPU 時間排序）
- 優化優先級

---

### 方法 3: 微基準測試 ⚡

**目標**: 測試單個組件的性能

**測試項目**:
1. **路由匹配速度**
   - 靜態路由 Map 查找
   - vs Hono 的路由匹配
   - 測量：1000 萬次查找的時間

2. **Context 創建速度**
   - FastContext.reset()
   - vs Hono Context 創建
   - 測量：100 萬次創建的時間

3. **JSON 序列化速度**
   - c.json({ message: 'Hello' })
   - vs Hono 的 c.json()
   - 測量：100 萬次序列化的時間

4. **對象池效率**
   - acquire + release
   - vs 直接 new Context()
   - 測量：100 萬次循環的時間

**輸出**:
- 每個組件的性能數據
- 識別最慢的組件

---

### 方法 4: Elysia 逆向工程 🕵️

**目標**: 理解 Elysia 為何比 Native 還快

**分析重點**:
1. Elysia 的路由實作
2. Elysia 是否使用了 Bun 的特殊 API
3. Elysia 的 Context 設計
4. Elysia 是否有編譯時優化

**步驟**:
1. 閱讀 Elysia 源碼（重點關注 `src/index.ts` 和路由部分）
2. 查找 Bun 專屬 API 的使用
3. 分析其優化技巧

**輸出**:
- Elysia 的關鍵優化技巧
- 可應用到 Gravito 的方法

---

### 方法 5: 記憶體分配分析 💾

**目標**: 測量每個請求的記憶體分配

**工具**: Bun 的 `--smol` 或記憶體 profiler

**測量**:
- 每個請求分配了多少記憶體
- 哪些對象佔用最多記憶體
- GC 頻率

**目標值**: < 1KB per request (根據 RFC)

**輸出**:
- 記憶體分配報告
- 需要優化的記憶體熱點

## 預期發現

基於當前 -2.1% 的差距，我預測可能的問題：

### 假設 1: 路由匹配開銷
- Gravito 的 Map 查找可能有額外開銷
- Hono 可能使用更優化的數據結構

### 假設 2: Context 重置開銷
- 即使重用對象，reset() 可能仍有開銷
- Headers.forEach + delete 可能比預期慢

### 假設 3: 函數調用層級
- Gravito 的調用鏈可能比 Hono 深
- 每多一層調用都有開銷

### 假設 4: async/await 開銷
- 過多的 async/await 可能拖慢速度
- 某些函數可能可以改為同步
